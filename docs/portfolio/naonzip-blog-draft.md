# 나온집 블로그/브런치 글 초안

## 제목 후보 3개

1. 부산 맛집 앱으로 시작해서, AI 운영 포트폴리오로 끝난 이야기
2. "이거 돈 되냐?" — AI랑 서비스 하나를 끝까지 만들어 보고 내린 결론
3. 사업화는 실패했지만 운영 능력은 남았다: 1인 + AI 서비스 제작기

---

## 본문 초안

### 1. 처음엔 "부산 방송맛집 서비스"였다

시작은 단순했다. 부산에서 방송·유튜브에 나온 맛집을 모아 보여주는 앱.
"방송에 나왔다"는 건 꽤 그럴듯한 후킹이라고 생각했다. 그래서 데이터를 모으고, 지도를 붙이고,
공유 버튼을 달았다. AI(Claude Code)와 함께 빠르게 골격을 만들었다.

### 2. 사용자 피드백에서 한계가 보였다

그런데 사람들에게 보여주니 반응이 미지근했다.

- "방송맛집만으로는 신뢰가 안 간다"
- "예약 기능도 없네?"
- "캐치테이블이 있는데 이걸 왜 써?"
- "솔직히 돈은 안 될 것 같다"

맞는 말이었다. 예약·웨이팅 인프라가 필요한 플랫폼과 정면으로 붙는 건 1인 제작 기준 비현실적이었다.

### 3. 방향을 "신뢰"와 "포트폴리오"로 틀었다

두 가지를 결정했다.

첫째, 제품 방향: "방송맛집"이라는 좁은 정체성을 줄이고 **"어디서 봤는지(출처)를 함께 보여주는
부산 맛집 큐레이션"** 으로 바꿨다. 방송·유튜브뿐 아니라 가이드(미쉐린)·로컬(비짓부산) 같은 출처를
칩과 링크로 붙일 수 있게 데이터 구조부터 다시 설계했다.

둘째, 사업 방향: 억지로 사업화하지 않기로 했다. 대신 **"AI로 서비스를 어디까지 만들고 운영할 수
있는가"를 보여주는 포트폴리오**로 정리하기로 했다.

### 4. 그 사이에 실제로 만든 것들

방향을 바꾸는 동안에도 만들 건 다 만들었다.

- **데이터 운영**: 후보를 모으고, 좌표를 지오코딩하고, 비공개로 적재한 뒤 검증을 통과해야만 공개되는
  파이프라인. 1회성 스크립트는 실행 후 지우고 리포트만 남겨 감사 추적이 되게 했다.
- **이미지 운영**: 저작권이 애매한 외부 이미지는 절대 쓰지 않았다. 운영자 실사진/공개 라이선스/생성
  placeholder만. 없으면 카테고리 이모지로 안전하게 대체했다.
- **SEO**: 구조화 데이터(JSON-LD), 동적 OG 이미지, ISR, 지역·프로그램별 랜딩 페이지까지.
- **Admin CMS**: 후보를 식당으로 변환하고 게시하는 워크플로, 편집, 제보 큐, 그리고 신뢰 출처를
  직접 입력·수정·삭제하는 화면.
- **신뢰 출처(Trust Source)**: 설계 → 운영 DB 적용 → 런타임 안전 조회 → Admin 입력 → 상세페이지
  표시 → 링크 검증 → 후보 리포트 → 실데이터 import까지, 끝단을 다 통과시켰다.

이 모든 걸 Phase 단위로 쪼개서, 매번 타입체크·빌드·실제 화면 노출까지 확인하고 문서로 남겼다.

### 5. 핵심 교훈

**(1) AI는 실행을 빠르게 하지만, 판단은 사람이 해야 한다.**
AI는 스키마를 짜고 UI를 만들고 검증까지 척척 했다. 하지만 "방송맛집은 신뢰가 약하다",
"사업화 대신 포트폴리오로 가자" 같은 방향 전환은 사람의 몫이었다.

**(2) 사업화와 포트폴리오화는 다르다.**
돈이 되는 서비스를 만드는 것과, 실력을 증명하는 자산을 만드는 것은 다른 게임이다.
무리해서 전자를 쫓다 둘 다 놓치느니, 솔직하게 후자를 택했다.

**(3) 작은 실서비스는 AI 운영 능력을 증명하는 좋은 자산이다.**
화려한 데모가 아니라, 데이터·이미지·SEO·Admin·신뢰 구조까지 "운영"이 돌아가는 작은 서비스.
이게 말보다 강하다.

### 6. 그래서 결론은

큰돈을 벌지는 못했다. 시장에서 검증했다고 말할 수도 없다.
하지만 **1인 + AI로 실제 운영 가능한 서비스와 운영 체계를 끝까지 만들 수 있다**는 건 남았다.

다음엔 이 능력을 다른 곳에 쓰면 된다.
